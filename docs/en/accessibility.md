# Documentation accessibility

The documentation is published as Markdown on GitHub. It is organized by task, by territory, and by the information you start with, with headings that say what they are about and with paths you can follow.

The same text in Spanish is [accesibilidad](https://comunidad-de-inteligencia.github.io/osint-atlas/accesibilidad/).

## What the validator checks

The validator checks that there is one main title, that headings do not skip a level, that internal links and anchors exist, and that an image has alternative text. It ignores headings inside a code block.

Those checks catch structural mistakes. They do not certify accessibility and they do not replace reading.

## How to read it before you hand work over

Walk through the README, the catalog, one territory, one entry, and one procedure. Each link should let you anticipate the destination. It should be clear what pending means.

Repeat the reading in a narrow window, about 320 CSS pixels, and with the browser at 200% and 400%. CSS means Cascading Style Sheets. The text should adapt and the essential controls should still be there.

Move through the links with Tab and open them with Enter. Focus should be visible and the order should be logical. If you use a screen reader, review the list of headings and links. Note the device and the result.

GitHub's own interface depends on GitHub. A finding should separate this project's content from the platform's controls.

## What to write down

Write down what could not be tested. A test that was not run stays pending. The date of that check is the exception that may be written.

Design reference: [the W3C reflow criterion](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html). W3C is the World Wide Web Consortium. WCAG means Web Content Accessibility Guidelines.

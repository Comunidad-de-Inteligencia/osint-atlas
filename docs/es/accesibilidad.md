# Accesibilidad de la documentación

La documentación se publica en Markdown dentro de GitHub. Se organiza por tarea, por territorio y por la información de partida, con títulos que dicen de qué van y con recorridos que se pueden seguir.

El mismo texto, en inglés, está en [accessibility](https://comunidad-de-inteligencia.github.io/osint-atlas/en/accessibility/).

## Qué comprueba el validador

El validador mira que haya un título principal, que los encabezados no se salten un nivel, que los enlaces internos y las anclas existan, y que una imagen tenga texto alternativo. Ignora los encabezados que están dentro de un bloque de código.

Esas pruebas cazan errores de estructura. No certifican accesibilidad y no sustituyen la lectura.

## Cómo leerla antes de entregar

Recorre el README, el catálogo, un territorio, una ficha y un procedimiento. Cada enlace tiene que dejar ver el destino. Tiene que entenderse qué significa pendiente.

Repite la lectura en una ventana estrecha, del orden de 320 píxeles CSS, y con el navegador al 200 % y al 400 %. CSS es Cascading Style Sheets, las hojas de estilo. El texto tiene que adaptarse y los controles esenciales tienen que seguir ahí.

Recorre los enlaces con Tab y ábrelos con Enter. El foco tiene que verse y el orden tiene que ser lógico. Si usas un lector de pantalla, revisa la lista de encabezados y de enlaces. Anota el dispositivo y el resultado.

La interfaz de GitHub depende de GitHub. Un hallazgo tiene que distinguir el contenido de este proyecto de los controles de la plataforma.

## Qué anotar

Anota qué no se pudo probar. Una prueba que no se ha hecho queda pendiente. La fecha de esa comprobación es la excepción que sí puede escribirse.

Referencia de diseño: [criterio de adaptación del contenido del W3C](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html). W3C es el World Wide Web Consortium. WCAG es Web Content Accessibility Guidelines, las pautas de accesibilidad del contenido web.
